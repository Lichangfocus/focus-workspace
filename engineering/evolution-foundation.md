## DSH 提供什么，产品还需补什么

| 已核查的 DSH 机制 | 本产品的设计用途 | 不能直接推导出的结论 |
| --- | --- | --- |
| Cordis 插件、服务、事件与可释放注册；配置组合形成插件树 | 能力按插件替换或装配，观察与改进逻辑通过扩展点接入 | 插件可装卸不代表文件、网络或其他副作用可撤销 |
| Agent Presets 与会话选择 | 给候选配置单独身份，让不同运行关联各自装配 | preset ID 不等于所有依赖、模型和外部服务都已经冻结 |
| 持久化会话事件与工具调用记录 | 作为执行事实，建立结果、反馈、候选、评估的引用关系 | 日志存在不等于产品已完成效果评估或因果归因 |
| Tool、Skill、MCP、Subagent 的既有扩展方式 | 让 Agent 的改进产出成为可复用能力 | 能力被发现或注册不等于已成功参与真实任务 |

本地参考：上游 `docs/architecture.md`、`docs/cordis-primer.md`、`packages/preset/agent-presets/README.md`，固定来源与版本见[上游记录](upstream.md)。产品不因新目标修改上游执行循环。

## 执行与改进分开管理

日常执行仍使用已采用版本和既有 DSH 权限、审批及会话通道。观察模块读取实际事件，保存任务结果索引；改进模块只接收选定任务和允许使用的上下文，输出候选；验证模块用单独会话与工作目录比较候选；版本模块决定后续新任务使用哪个版本。它们可以先是同一 Host 插件中的明确职责，不要求 P1 拆成多个进程或服务。

候选验证即使使用独立 preset，也不自动获得文件或网络隔离。P1 对会写文件的案例使用专门复制的输入与输出目录，沿用 DSH 审批；发信、发布和其他外部写入不盲目重放，使用受控测试目标或标为未验证。未来生成插件代码时再增加独立进程与测试发布路径。

## 最小持久化对象

所有对象带格式版本、账号、创建时间与作用域，使用稳定 ID；不可用的证据位置或依赖标记缺失。以下为新增字段设计，不声称 alpha.2 已存储完整信息。

| 对象 | P1 至少保存 |
| --- | --- |
| TaskRun | run ID、session/事件定位、workspace、任务与成果引用、实际 Harness 版本、执行状态、客观错误、起止时间和可获取用量 |
| HarnessRevision | revision ID、父版本、DSH/应用版本、preset 快照、Skill 内容摘要或快照、工具/插件实际版本、模型及参数、指令/上下文来源和权限策略引用；凭证只存引用 |
| Feedback | 关联 run ID、用户明确反馈、可用/需修改/失败、纠正内容引用、作用域、作者和时间；Agent 推断与用户反馈分开 |
| ImprovementCandidate | 候选 ID、基准 revision、来源 run/feedback、改进目标、对象、差异/产物、预期指标、依赖、状态和失败原因 |
| Evaluation | 基准与候选 ID、冻结输入/规则版本、验证运行引用、逐项结果、人工判定、环境差异、未验证项及可获取成本 |
| Adoption | 候选与证据引用、采用/拒绝/回退决定、操作者、原因、此前与目标默认版本、生效范围与时间 |

DSH 日志保持执行事实的唯一来源；产品只补它没有的关系和反馈，不复制另一套聊天历史。当前原子 JSON 可用于最小记录；数据量或查询需求成立后再迁移 SQLite，不为长期路线一次性建齐全部表。大文件保留内容摘要和受控快照，外部可变服务记录版本或不可冻结限制，不宣称能精确重演所有世界状态。

HarnessRevision 是产品的整体运行依据。即使 alpha.2 只复制 preset 和 Skill，后续也须把 Host 级模型设置、权限与上下文记录到每次运行；运行时读取的实际值优先于界面默认值。旧会话受可变 Host 设置影响时明确展示差异，不能仅凭 preset 名称声称整个环境未变。

## 变更、冲突和恢复

候选状态依次为草稿、待验证、验证中、有效/无效/证据不足、已采用/已拒绝；采用后可以记录回退。每个状态变化保留证据和原因，生成成功不自动跳到已采用。

应用前比较候选基准与当前默认版本；默认版本已变化时重新生成或验证，禁止覆盖用户后来的手工修改。应用操作串行化，记录实际加载结果后原子更新默认指向；失败仍保留原默认，并可在重启后识别未完成采用。运行中的任务固定实际版本关联，新默认只作用于新任务。回退校验旧版本和依赖可用性，不覆盖历史评估或撤销已发生的外部动作。

产品发布版本、Harness/Skill 版本和用户数据版本独立管理。用户数据恢复需兼容原应用和日志格式，源码 Git 回退不能替代数据恢复。删除来源后，候选/评估引用显示不可用并停止后续使用；私有内容不自动转成全产品共享能力。

## MVP 的两条验收线

日常助手沿用 P1 真实对话、历史、文件、审批、停止和成果验收。进化基础增加一条受控 Skill 改进案例：能从成果返回来源任务与实际配置，记录明确纠正，生成候选，在独立目录与原版本比较，采用后新任务生效，回退后不再采用候选，并保留每步依据。

重点覆盖：候选加载失败不改默认；验证不合格不能标为有效；默认被手工修改后旧候选不能覆盖；新旧任务版本关联正确；断线或重启不会重复采用；数据作用域和凭证引用不泄漏。涉及模型调用的验收使用真实运行，不用工具清单发现代替。

## 与当前 alpha.2 的差距及实现顺序

1. 先完成已接入对话链路的真实模型任务验收，同时补 TaskRun 与实际 HarnessRevision 关联。
2. 在对话成果处增加显式反馈，Harness 增加相关任务/反馈引用。使用现有日志和轻量记录，先不建设知识库。
3. 以一个本地 Skill 为改进对象，复用当前不可变配置版本机制，增加候选、差异和独立验证记录。
4. 增加采用前冲突检查、采用记录和回退原因，完成一条实际闭环；再扩展批量评估、更多进化对象及自动化。

alpha.2 已有独立账号目录、官方执行日志、Skill 快照、preset 应用与手动回退。alpha.5 在此基础上增加模式内反馈、配置候选、比较证据与采用记录；具体已验收范围见[清单](../product/features.md)。

## alpha.5 落地

模式编辑由 Host 统一处理。每模式保存观测/进化属性、反馈、候选、基准修订和证据；生成器使用无执行工具的临时极简装配，通过 SessionController 提交真实提示词。候选试跑使用独立 preset 和 session；采用需要两侧模型回复与用户对照证据，并校验基准版本和草稿修订。尚未提供自动评分、自动发布或 Skill 文件内容生成。
