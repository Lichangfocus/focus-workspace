## 一、定位

**Focus Workspace 是面向超级用户的开源个人 Agent：以 DeepSeek Harness 为底座，提供一个灵活、可控可见、能自进化的 Harness，并在其上构建工作台、主动性、系统连接、个人知识库和 Agent 网络。**

对外的核心亮点是 **自进化** 与 **可控可见**，二者是一体的：看得见 Agent 如何工作，才能控制它；控制得住每一次改变，才能放心让它进化。

## 二、目标用户

**主画像：因 AI 而具备开发能力的高级知识工作者。** 他们不是职业开发者，但借助 AI 已经能写脚本、写 Skill、接 MCP、改配置；日常同时使用多个 AI 工具，有长期积累的方法论和资料。

| 他们要的 | 他们不要的 |
| --- | --- |
| 看清 Agent 用了什么指令、工具和上下文 | 不透明的黑盒助手 |
| 按任务组合能力，配置可版本化、可回退 | 一次性配置、改坏了回不去 |
| 纠正一次，下次就会，经验沉淀在自己账号里 | 每次重新解释背景和偏好 |
| 连接自己的电脑、服务和数据 | 只能聊天、不能做事 |

待验证假设：这类用户愿意为“可控可见 + 自进化”放弃部分开箱即用的简单性。首个实例用户是项目作者本人，产品能力面向其他同类用户设计，个人数据属于账号而不写入产品。

## 四、为什么以 DSH 为底座

DSH 是全插件架构的 Agent Harness：执行循环、模型接入、工具、会话日志、Skill、MCP、Subagent、沙箱都是可替换插件，preset 可以声明完整装配，会话日志能重建每一次模型请求。这正好提供了“灵活组合”和“可见”的底层条件。

| DSH 负责 | Focus Workspace 负责 |
| --- | --- |
| 执行循环、模型、工具、会话日志、Skill/MCP/Subagent 加载、审批与沙箱 | 模式的身份、草稿、版本与会话绑定 |
| preset 与 profile 装配 | 按需组合、依赖检查、差异与发布 |
| 会话事件记录 | 运行观测、上下文可视、任务证据 |
| — | 反馈 → 候选 → 验证 → 采用 → 回退的自进化闭环 |
| — | 账号化的个人经验与工作台体验 |

原则：上游已有的通用能力直接使用，上游发布了与本产品重叠的能力时优先迁移过去；Focus Workspace 的精力放在上游不会做的部分。跟进方式见 [AGENTS.md](../AGENTS.md#上游跟进)。

## 五、第一件事：P1 Harness 底座

**目标：一个强大的 Harness 底座，能灵活按需组合、可控可见、能自进化，并用一条真实任务证明。** 对话作为运行面随 P1 交付；工作台桌面、主动性、知识库和协同都不进入 P1。

| 方向 | alpha.5 已有 | 修订 13 要补齐 |
| --- | --- | --- |
| 灵活组合 | 四种内置模式与自定义模式，独立草稿、发布、回退、恢复原版 | 按需组合（HARNESS-05）；每模式固定模型、权限建议；复杂 Subagent 详情 |
| 可控可见 | 实际插件/工具清单、指定会话的模型与工具观测 | 上下文与指令可视（HARNESS-06）；完整错误区分与能力详情 |
| 自进化 | 反馈 → 配置 JSON 候选 → 试跑 → 人工对照 → 采用 → 回退，已用算术样例跑通 | Skill 文件候选（EVOLVE-02 剩余部分）；用真实任务按预定规则验收 |
| 底座稳定 | 锁定 DSH 0.1.6-alpha.2，两处本地补丁 | 评估并升级到 0.1.7（TASK-030）；0.1.7 的 profile YAML 组合能力可能改变模式与按需组合的实现方式 |

## 六、贯穿验收场景：产品方案与行动清单

用本项目自己的方案文档作为输入，让 Focus Workspace 为 Focus Workspace 产出“下一阶段产品方案摘要与行动清单”。完整任务、验收规则和通过条件见[自进化 · P1 验收用例](features/self-evolution.md#p1-验收用例产品方案与行动清单修订-13-草案待对齐)。

1. 在 Harness 选择或组合一个模式，装配方案类 Skill 与需要的工具，检查并发布。
2. 用冻结的项目资料发起任务，处理审批，得到真实成果，并能查看本次请求实际带了哪些指令和上下文。
3. 按预先写定的规则逐项判定成果，对不通过项写反馈，选择“改进做法”。
4. Agent 生成 Skill 候选，查看差异；在同样输入下运行目标任务与两个相邻任务，对比结果。
5. 满足通过条件后采用，新任务使用新版本；旧会话仍能追溯原版本。效果退化时回退。
6. 重启后成果、反馈、候选、验证和采用记录都可追溯。

两个结果都要成立：**今天的方案任务做得方便；这次纠正改善了下一次。**

## 十、产品原则

1. **真实优先**：只有真实运行、真实任务和真实证据能推进功能状态；Demo、模拟与加载成功都不算完成。
2. **可见才可控**：配置、实际加载、实际调用与任务效果分别展示，未知就标未知。
3. **改变必须可追溯、可回退**：模式版本不可变，旧会话不被静默改变，进化候选先验证后采用。
4. **经验属于账号**：个人偏好、Skill 改进和资料属于用户的账号与工作区，不写入产品代码。
5. **上游优先**：能用 DSH 的不自己造，重叠能力向上游迁移。
6. **方案先行**：先在本大纲和功能设计中确定方案并获得确认，再写代码。
