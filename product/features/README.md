## 写法规范

每份功能设计文档：

1. 标题下第一行是所属信息：`> 所属：产品大纲 · 支柱 · 功能 ID · 功能项与进度见下文`。
2. 紧接着是「功能项与进度」表（ID、功能、阶段、状态、完成条件）。每个功能 ID 只出现在一份文档的表里，这张表是它阶段与状态的唯一来源。
3. 正文按需包含：目标（解决什么问题）、用户操作与结果、规则与边界、数据与状态、实现约束（依赖哪些 DSH 能力、有哪些待工程验证项）、验收、待确认。
4. 新功能在所属模块文档的表里分配 ID；状态变化后同步更新大纲中该模块的“当前进度”一句话。一个模块变大时拆成新文档并更新本索引。
5. 尚未确认的设计标注“草案，待对齐”；用户确认后在[确认记录](../approval.md)登记，才能进入工程。
6. 历史修订说明保留在文档内，但当前行为写在前面；过时内容直接改写，不叠加“修订 N 补充”。

## 功能项与状态

状态依次为：待细化 → 待对齐 → 可开发 → 开发中 → 待验收 → 已验收；明确后置为“延期”。alpha.5 期间使用的“已实现 / 部分实现 / 真实样例通过”保留原样，表示已有真实实现但尚未完成完整验收。“可开发”须有[确认记录](../approval.md)；“已验收”须有真实产品证据链接。沿用既有 ID，一个功能跨阶段时用 `.1`、`.2` 拆分。`CHAT-01` 类为产品功能，`TASK-001` 类为[待办](../../iterations/backlog.md)中的执行任务，两者不混用。
