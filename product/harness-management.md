# 第一期：对话与 Harness 管理

统一审阅与开发基线见[完整产品方案（修订 12）](brief.md)。本页保留专题细节及历史演变，不作为另一份待确认方案。

方案：0.1-draft，修订 12。日期：2026-09-23。用户已明确第一期只设计对话与 Harness 管理，包括 tool、skill、MCP 等装配，以及 Harness 现状可视化。本页定义完整 P1 行为；alpha.5 已实现模式编辑和模式内观测、受控进化基础；完整 P1 与本版范围仍须区分。分期与状态统一维护在[功能清单](features.md)。

## 产品结构

第一期只有两个主要工作入口：“对话”和“Harness”。本地账号、模型凭证与数据归属作为必要基础设置，不另做一套完整账号管理产品。长期能力广场中的本地装配管理先收进 Harness，不同时设计两套重复入口；在线发现、市场和首页桌面插件安装均后置。

对话负责做事；Harness 管理负责说明当前能做什么、这些能力来自哪里，以及如何调整装配。两处通过实际使用的配置版本和能力记录关联。方案修订 8 加入方便使用与自进化双目标：反馈由对话结果产生，候选、验证和采用在 Harness 内管理，不新增一个复杂主入口。

## 对话

保留新建与历史会话、输入与流式回复、工作空间和文件引用、工具执行记录、审批、补充信息、停止任务、成果查看与继续修改。对话能查看本次采用的 Harness 版本和可用能力摘要，能力名称可定位到管理详情。P1 默认一个前台执行任务，不扩展桌面 Pin、知识整理或定时调度。

新对话优先使用显式选择的模式及具体版本，未选择时用账号默认；发布模式不自动修改默认。已有会话显示自己的配置版本；管理页变更不静默替换运行中的装配。建议第一期以“使用新配置新建对话”作为明确切换方式，旧会话使用旧配置继续前须核验旧版本可用性，无法重建时说明原因，不暗中套用最新配置。

## Harness 现状总览（HARNESS-01）

总览同时提供关系视图与可读清单。默认展示选中模式的配置及其检查状态；可切换查看指定对话的实际绑定，二者不能用同一默认运行实例代替。关系视图是状态展示，第一期不做任意拖拽式流程编排。

| 内容 | 展示内容 |
| --- | --- |
| 运行环境 | DSH 版本、配置版本、运行状态和最近加载时间 |
| 模型与指令 | 当前模型、指令及上下文来源摘要；支持的配置入口，敏感内容不展示 |
| Tools | 可用工具、来源、本地或 MCP 提供、权限及错误 |
| Skills | 已装配 Skill、来源和版本、启用/加载情况，以及本次会话是否调用 |
| MCP | 服务连接状态、配置来源、授权状态、实际发现的工具及归属关系 |
| Subagent | 已装配的子 Agent 或预设及可观察的能力关系，不画不存在的执行者 |
| 执行权限与会话 | 当前权限策略、适用范围、关联会话及装配版本 |

明确区分“已配置”“待应用”“已加载”“可调用”“故障”和“未知”。已勾选启用不等于运行成功；未能取得实际状态时标记未知及原因，不以静态配置冒充运行结果。关系只来自可验证的装配、声明或运行记录，不把猜测的 Skill→Tool 依赖画成确定事实。

## Tool 管理（CAP-03）

查看工具名称、用途、参数说明、提供方、版本或来源、当前状态及权限范围。管理的是工具提供插件或提供方的装配，以及运行时支持的工具级控制；不能给不支持单项关闭的工具提供虚假的开关。MCP 提供的工具保留所属服务关系，从工具详情可进入 MCP 配置。

首期提供已支持来源的配置、启停与检查；不默认实现任意代码编写器或工具市场。执行验证显示真实输入与结果，可能产生副作用的测试沿用正常审批。移除检查依赖，错误说明缺少什么配置或能力，不静默跳过。

## Skill 管理（CAP-01.1）

导入本地 Skill 目录，查看指令与资源、来源和版本，配置适用范围并启停；重复或无效导入有明确反馈。Skill 被加载、可被选择和实际参与过对话分别展示。验证入口创建一条真实对话，结果回链到该 Skill 和配置版本。

Skill 是给 Agent 使用的指令及资源，不是定时任务，也不因装配而自动获得文件、工具或连接器权限。第一期不强制解析出不存在的标准化依赖声明；能确定的依赖展示，未声明部分按实际执行记录解释。

## MCP 管理（CAP-01.2）

添加或导入服务配置、编辑必要连接参数和凭证引用、检查连接、查看实际发现的工具、启用或停用、重连及移除。连接失败、授权失败和工具发现失败分别显示，不因配置保存成功而显示已连接。

本地进程型和远程服务型是完整设计中的连接类型；第一期至少选定并真实验证一种上游支持的接入方式，另一种未通过接入验证前不得显示为可用。具体支持类型由技术验证与 Demo 对齐后固定，不提前宣称两种都实现。添加进程命令会启动本机程序，界面应显示命令与参数及所需授权；凭证以账号内安全引用保存，不回显或写入普通任务记录。

从 MCP 导出的工具展示同一来源，不复制成相互独立的工具配置。服务停用后，新配置下的对话不再获得其工具；运行中会话按既定配置与停止规则处理。

## 其他装配（CAP-01.3.1、SETTINGS-01）

首期建议覆盖已有 Subagent 预设的查看、选择和装配状态，能够解释其职责、模型及能力范围；复杂的子 Agent 编辑与派发管理界面安排后续。模型、系统指令和权限仅为已验证的可配置字段提供编辑，其他内容只读并解释来源。用户尚未指定的其他装配类型不自动扩大为首期必交项。

## 配置应用与恢复（CAP-02.1、HARNESS-02.2）

统一链路为：编辑草稿 → 校验与依赖检查 → 查看差异和影响范围 → 发布本模式版本 → 明确选择开始对话或设为默认。保存草稿、成功应用与实际调用三个状态分开。应用失败保留上一份可用配置并展示原因；需要重启时说明影响，先处理运行任务，不强制终止未确认的工作。

每次成功应用保留配置版本、能力来源与可获取的依赖版本。回退先校验旧依赖与凭证引用是否仍可用，不具备恢复条件时明确失败；不能只切一个版本号就宣称运行时已回退。回退用于后续对话，不撤销已发生的工具副作用，历史记录保留原始关联。第一期包括这种手动管理与回退；P1 增加由用户发起、Agent 生成 Skill 候选的最小验证闭环；批量评测、自动触发及自动改写内核留到后续。

## 从任务反馈改进做法（EVOLVE-01～04）

对话成果处提供“可用 / 需要修改 / 失败”和可选原因，用户可选择只处理当前成果，或“改进做法”。后者携带选定任务和反馈进入 Harness；先选择项目作用域，默认不提升为账号通用偏好。

Harness 内展示候选改了什么、基于哪个版本、引用哪些反馈，以及待验证/有效/无效/证据不足状态。P1 先针对一个本地 Skill；用户可查看差异、发起受控验证、比较结果、采纳或拒绝。采用前发现当前配置已变化时提示重新验证，不能覆盖新的手工修改。配置历史补充来源候选、验证记录与采用/回退原因。

本页只定义入口与交互；候选状态、评估条件及自动化边界统一见[自进化设计](self-evolution.md)。不要求用户先理解插件源码或维护评测平台才能提交一次反馈。

## 第一阶段验收

1. 在管理页装配一个真实可用的 Tool、一个本地 Skill，以及一种受支持的 MCP 服务；可看到服务及工具来源关系。
2. 应用配置后，总览与实际运行一致；缺失、故障和待应用状态有可复现样例。
3. 新建对话使用该配置，完成一次真实文件任务；验证 Skill 参与及 MCP 工具调用，并能从执行记录定位能力来源。
4. 审批、拒绝、提问、停止、模型或连接失败及成果继续修改均真实有效；重启后能读取历史与配置记录。
5. 停用或修改能力后，新配置下的新对话使用正确装配；旧对话版本关系不被改写。应用失败保留可用配置，手动回退经过真实加载与调用验证。
6. 本地账号归属、凭证保护、安装包独立启动及兼容备份恢复通过检查。
7. 从一个真实任务的用户纠正生成 Skill 候选，关联基准与验证结果，经用户采用后新任务使用新版本，回退可追溯；无效候选不能自动生效。

上述是建议的详细验收条件，具体界面通过 Demo 对齐。P1 不依赖首页插件桌面、小组件调度、知识库、跨人协同或批量 A/B 平台；受控候选比较属于 P1。

## Demo 联动

下一版聚焦两条相连链路：Harness 总览 → 添加/装配能力 → 校验并应用 → 从该版本发起对话；对话执行 → 查看调用来源 → 返回 Harness 详情 → 修改并应用 → 新对话验证。补齐配置错误、MCP 断连、加载失败、待应用、旧会话版本和回退等状态。Demo 仍明确使用模拟数据，正式验收必须由真实运行状态驱动。

修订 8 的交互对齐增加“成果反馈 → 候选差异 → 基准/候选结果 → 采纳/拒绝 → 新任务 → 回退”，包括证据不足、版本冲突和验证失败状态。现有 Demo 与 alpha.2 均未覆盖新增闭环。
